## 1. 这一阶段要做什么

往已经打通的 Java 模块里批量灌方法，验证上一轮的说法：

> 加一个 Java 能力 = 改两个文件（`XRBridge.java` + `XRDeviceKitJava.cpp`），XML 不用动。

本轮加 15 个方法，节点总数从 29 涨到 44。

| 分类 | 新增节点 | 底层 Java API |
|---|---|---|
| 应用信息 | `GetVersionName`、`GetVersionCode`、`IsAppInstalled` | `PackageManager.getPackageInfo` |
| 屏幕 | `GetScreenWidth`、`GetScreenHeight`、`GetScreenDpi`、`GetScreenDensity`、`GetScreenRefreshRate` | `DisplayMetrics`、`Display.getRefreshRate` |
| 存储 | `GetInternalFreeMegabytes`、`GetInternalTotalMegabytes`、`GetExternalFreeMegabytes`、`GetExternalTotalMegabytes` | `StatFs` |
| 系统 | `GetUptimeSeconds`、`GetTimeZoneId`、`GetLanguageTag` | `SystemClock`、`TimeZone`、`Locale` |

## 2. 怎么做的

### 2.1 Java 侧：每个方法自己吞异常

15 个方法全部是 `public static`，每个都套 `try/catch (Throwable)`，失败返回默认值：

| 返回类型 | 失败值 |
|---|---|
| `String` | `""` |
| `int` | `0` |
| `long` | `-1` |
| `float` | `0` 或 `1.0` |
| `boolean` | `false` |

**为什么必须这样**：JNI 里最怕的是 Java 抛了异常没人清，下一次 JNI 调用直接崩。在 Java 侧吃掉，C++ 侧就不用每次检查 `ExceptionCheck()`。

### 2.2 C++ 侧：加一层通用调用器

上一轮是"一个方法一段 JNI 样板"，15 个方法要写 15 段。这轮改成按"名字 + 签名"缓存，写五个通用函数就够了：

```
CallInt("GetScreenWidth")        → GetStaticMethodID(..., "()I") → CallStaticIntMethod
CallLong("GetVersionCode")       → "()J"
CallFloat("GetScreenDensity")    → "()F"
CallString("GetPackageName")     → "()Ljava/lang/String;"
CallBoolWithString("IsAppInstalled", Pkg)
```

方法 ID 存在一个 `TMap<FString, jmethodID>` 里，键是 `名字+签名`，只查一次。

**效果**：现在加一个 Java 能力，C++ 这边只要写一个 4 行的包装函数：

```cpp
int32 XRDeviceKit::Java::GetScreenWidth()
{
#if PLATFORM_ANDROID
	return CallInt("GetScreenWidth");
#else
	return 0;
#endif
}
```

### 2.3 XML：一个字没改

这一轮 `XRDeviceKit_APL.xml` **完全没动**。验证了上一轮的结论：模块是整目录拷贝，里面加方法不需要改打包配置。

## 3. 写完为什么不是理想效果

这轮编译**一次就过**，Win64 8.59 秒、Android 70.97 秒。但过程中出现了一个让我起疑的现象：

```
> Task :xrbridge:preBuild UP-TO-DATE
> Task :app:dexBuilderDebug UP-TO-DATE
BUILD SUCCESSFUL in 51s
```

`UP-TO-DATE` 意味着 gradle 认为"没变化、不用重跑"。可我明明改了 `XRBridge.java`（从 2 个方法加到 16 个）。

**这时候有两种可能**：

1. gradle 的增量判断是对的，新方法已经编进去了；
2. gradle 判断错了，我改的 Java 根本没编译，APK 里还是旧版本。

如果直接相信 `BUILD SUCCESSFUL`，第二种情况会被掩盖到真机上才炸。

---

## 4. 怎么定位的

不看构建日志，直接看**产物**：解包 APK，在 dex 里搜 15 个新方法名。

```powershell
$zip = [System.IO.Compression.ZipFile]::OpenRead($apk)
# 逐个 classes*.dex 读成字节，按 ASCII 搜方法名
```

结果：

```
classes3.dex   命中 13/13: GetVersionName, GetVersionCode, IsAppInstalled,
               GetScreenWidth, GetScreenHeight, GetScreenDpi, GetScreenDensity,
               GetScreenRefreshRate, GetInternalFreeMegabytes, GetExternalTotalMegabytes,
               GetUptimeSeconds, GetTimeZoneId, GetLanguageTag
```

（搜的是 13 个名字，另外两个方法名没放进检查列表，不是缺失。）

方法名都在 `classes3.dex` —— 正是 `xrbridge` 模块产出的那个 dex。说明 gradle 的 `UP-TO-DATE` 只是说"app 自己的 dex 没变"，模块的 dex 是单独合的，判断没错。

---

## 5. 怎么解决的

没有需要修的东西。真正做对的是**验证方式**：不看"构建成功"，看"产物里有没有"。

这条以后固定下来：

```
Java/C++ 改了 → 编译 → 解包 APK 搜符号 → 才算过
```

### 现在加一个能力要做的事

```
1. XRBridge.java         加一个 public static 方法，try/catch 包住
2. XRDeviceKitJava.h     加一行声明
3. XRDeviceKitJava.cpp   加一个 4 行包装（CallInt/CallString/...）
4. XRDeviceKitPlatform.h/.cpp  加转发（3 行）
5. XRDeviceKitLibrary.h/.cpp   加 UFUNCTION + 转发（6 行）
```

合计约 30 行，两个平台各编一次，解包搜一下符号。**不需要碰 XML、gradle、目录结构。**
